# Optional external adapters

`channels.py` contains the single Telegram/Slack message delivery implementation used by MCP verification and workflow notifications. It has no startup/container imports. `find_channel_connector(database, provider, organization_id)` selects a connector only from the supplied tenant's catalog. `resolve_telegram_target` retains configured-chat placeholder resolution. `deliver_channel_message` accepts a configured connector, target and text, sends once with a five-second timeout, and succeeds only after HTTP 200 and provider `ok=true`.

Telegram uses bot_token and chat_id/allowed_channels; Slack uses bot_token and the selected channel through chat.postMessage. Missing credentials/connectors or unsupported providers raise ChannelDeliveryError. Exceptions shown to users omit credential-bearing URLs and provider bodies. There are no automatic retries or simulated successes.

MCP POST `/api/v1/mcp/test-channel-message` returns 503 for an absent connector, 400 for delivery/configuration rejection, and the existing success envelope with delivery=delivered only on acknowledgement. If an audit actor exists, mcp_tool_calls progresses STARTED → COMPLETED or FAILED. No new schema columns are introduced.

WorkflowNotifier is an optional composed adapter; notification exceptions never change workflow execution outcome. Audit IDs use call_notify_{execution_id}; an existing call is not automatically resent. Unconfigured connectors/no audit actors are logged as unavailable without claiming delivery. Delivery acknowledgement/audit are not a transactional exactly-once guarantee; no outbox or retry worker is introduced. All source files stay at most 500 physical lines. No messages were sent and no runtime checks were performed in this task.

## Governed workflow execution tools
New modules are independent of backend startup/router imports:
- tool_definitions: hard-coded executable inventory, strict Pydantic RepositoryInput(repository,days=7,1..90) and MessageInput(channel_id,text<=60000), real resource ID validation, and deterministic implementation metadata registration. Canonical GitHub tools are get_repository_activity/list_commits/list_issues/list_pull_requests/list_releases; Telegram send_message and Slack post_chat_message. Unknown providers/actions are unsupported, never simulated. ensure_tools may register missing mcp_tools metadata but never creates/changes grants. Department wildcard grants cover newly registered implemented tools; explicit lists must include the requested names.
- tool_scopes: execution/step snapshots in server-owned SQLite records. Bound org/department/workflow/execution/task/agent/current initiator; declared connectors/resources/tools cap access. All steps of an integration-backed workflow receive a scope, even model-only steps with no tools. Empty agent permission configuration delegates only the explicitly governed workflow scope; nonempty agent config/database grants further restrict tools. dangerously_skip_permissions never bypasses connector policy. Live task/execution, expiry, initiator status/role/membership, current agent/tenant, connector status, resource allowlists, department/tool grants and budget are rechecked per call. Permission/config growth cannot expand a captured scope; revocation invalidates use.
- provider_http: stdlib HTTPS to fixed api.github.com/api.telegram.org/slack.com hosts, verified TLS, 10-second socket timeout, <=2 MB responses, no redirects, proxy inheritance, caller URLs, credential-bearing logging or automatic retries. Provider bodies/headers are excluded from errors.
- github_activity: authenticated read-only commits/issues/PRs/releases, API version 2026-03-10, UTC lookback and bounded pagination (3 pages of50 per category; <=45000 projected content characters). Issues/PRs use updated_at; releases use published_at; ordinary tags are excluded. Cap-hit output explicitly marks partial=true. Only selected fields are returned, tagged untrusted_external_data; no repository script/content executes. Permissions are rechecked before/after each HTTP request.
- scoped_channels: literal Telegram numeric IDs/@channel usernames or Slack C/G IDs; no alias guessing, first-channel fallback, Markdown execution, external link previews or arbitrary methods. Slack mention/control delimiters are escaped. Sends succeed only on HTTP200 and provider ok=true. A dispatched message cannot be rolled back by later cancellation.
- tool_executor: runtime tool schemas narrow repository/channel enums to the frozen scope; model-supplied credential/URL/identity fields are forbidden. Each actual invocation atomically claims a deterministic call_exec_ audit ID before I/O; at most32 new connector calls per step. Duplicate reads reuse a successful receipt after fresh authorization. Delivery is at most one attempted logical report per task/connector/channel; changed text or unknown/failed attempts are not retried. Calls progress STARTED→COMPLETED/FAILED. Known denied tools use call_denied_ FAILED audits without hostile arguments. Message audits store only channel ID + text SHA256, not message bodies or credentials. Read results are persisted as private audit data. Completion checks require receipts for every declared repository/channel and explicitly requested operation; prose is insufficient. These are application audit records, not a tamper-proof/exactly-once system.
- notification_guard: frozen completion binding, exact connector lookup, current initiator/grant/tool/channel checks and a real execution agent as audit actor. An explicit successful send step suppresses duplicate completion delivery to that destination. Atomic call_notify_ claims forbid ambiguous resend; notification failure remains an optional delivery failure rather than fabricated success or a changed model result.
Existing channels.py remains the separate legacy manual verification/ChatOps adapter; governed runtime/notification execution uses the stricter scoped_channels implementation. Nothing here is an OS sandbox or a defense against arbitrary trusted backend code. No GitHub writes, GitLab/Trello/SQL/filesystem tools or CLI-MCP bridge are implemented in this version. Tests were added as source only; no execution or live calls were performed.

Optional delivery correction: invalid completion-notification configuration is persisted as notification_error inside workflow_execution_tool_contexts and does not abort authorized data steps. Explicit send steps still fail when their required destination is invalid. A step with authorized_resources uses only the referenced subset of its declared mcp_servers (older builders copied notification connectors into all steps); unrelated connector declarations do not authorize sends. Optional notification failures remain blocked/audited without converting a good summary into a failed model run.

Manual MCP channel tests now reuse scoped_channels, including exact target and provider receipt checks; channels.py remains for legacy ChatOps callers only.

provider_http reads bounded error bodies and maps recognized Telegram rejection descriptions to fixed safe diagnostics (missing chat, bot membership/posting rights, blocked bot, migrated group, bad token, rate limiting). Unrecognized response text, migrated destination values and credentials are never reflected. No permission/target changes or retries occur automatically.

Telegram diagnostics additionally recognize bots-cannot-message-bots, bot-cannot-initiate-user-conversation and deactivated-recipient rejections using fixed safe text. No raw response is exposed and no destination is automatically changed.

Notification diagnostics preserve ToolAccessError safe policy/provider messages in both mcp_tool_calls.error and the surfaced notification_error. Unexpected exception details remain generic to avoid credentials. Existing failed/unknown claims are never retried automatically; earlier generic errors cannot be reconstructed.

## Lossless multipart reports
message_parts.py splits plain-text reports up to60000 Unicode characters into
parts <=3500 UTF-16 units, including [i/n] headers when multipart. Content and
whitespace are preserved, with preferred newline/space boundaries; no ellipsis.
scoped_channels sends sequential parts with3.1-second spacing between parts of
this report and reauthorizes each part. Pacing is not a global rate-limit guarantee.
A logical report is one existing atomic audit claim, not a claim per part. All
parts must return verified receipts before COMPLETED. Receipts retain the first
provider_message_id plus provider_message_ids and parts_delivered. Failures retain
acknowledged-count diagnostics; failed/unknown batches never automatically resume
or resend, even after partial delivery. No individual chunk-progress transaction
or exactly-once guarantee is introduced. Manual test input remains <=3500 chars;
runtime MessageInput permits <=60000. Tests and live calls were not run.

## Repository workspaces (`repo_workspace.py`)
Not a model-callable tool. Server-owned operations `clone_repository` and `open_pull_request` get metadata-only mcp_tools rows (`tool_repo_<sha>`) for agent permission and audit checks; they are not added to OPERATIONS. authorize_workspace rechecks the execution context initiator, tenant/department agent, CONNECTED GitHub connector, credentials, repository in allowed_repos, department grants (open_pull_request must be explicit; `*` is rejected for writes), agent MCP restrictions and budget. It runs before clone, before push and before PR creation. Host git ignores system/global config, disables hooks/fsmonitor/symlinks/submodules/redirects/non-HTTPS protocols, and receives the token only via GIT_CONFIG_* env extraHeader. Clone: depth 1, single branch, no tags, --separate-git-dir outside the mount, worktree .git pointer removed; every later git call passes explicit --git-dir/--work-tree. Publish: add --all, reject .github/workflows/, .github/actions/, .gitmodules, >200 files or >50000 changed lines, commit --no-verify, push HEAD to a new branch with an empty --force-with-lease (branch must not exist), then POST /repos/{repo}/pulls draft=true (provider_http.request_json now takes accepted statuses; 201 here). The PR body fences untrusted model output. Audits are `call_repo_<sha256(task:operation)>` STARTED→COMPLETED/FAILED with no automatic repeat. git stdout/stderr is never surfaced. Storage: workflow_repo_workspaces(task_id, execution_id, workspace_json) with state ACTIVE/RELEASED. Static review only; no GitHub calls were made.

## Workflow secrets (`workflow_secrets.py`)
store_secret validates UPPER_SNAKE names (rejecting reserved names, PLATFORM_* and DOCKER_*), at most 50 per workflow, 32 KB per value, and exactly one of value/external_ref. Encrypted values use AES-256-GCM (cryptography) with PLATFORM_SECRETS_KEY (base64 of 32 bytes) and AAD `workflow-secret:v1:<workflow>:<name>`. External values are AWS Secrets Manager ARNs limited to PLATFORM_EXTERNAL_SECRET_ARN_PREFIXES, rechecked at use and fetched with lazily imported boto3; provider errors are replaced by fixed text. resolve_workflow_secrets is all-or-nothing and checks the row's organization. repo_workspace.open_workspace resolves settings/secrets after authorization and before cloning, writes a host-only 0600 redactions.json when secrets exist, starts egress when allowlisted, and records machine_size/egress/secret_names (never values) in workflow_repo_workspaces. publish_workspace refuses changed files containing any secret value (>=4 chars). Storage: workflow_secrets table (UNIQUE workflow_id+name, ciphertext/nonce BLOB or external_ref, FK cascade) through WorkflowSecretsRepository: list (metadata only), get material, upsert, delete.

Existing prepare_execution_context validates the pinned sandbox image after current workspace authorization and before any workflow step/start notification. No Docker/network calls in this preflight. Explicit open_pull_request grants remain required; wildcard grants do not cover writes. No grants were edited. Source review only.


prepare_execution_context also validates the pinned proxy image before steps when workflow settings enable network_allowlist. No proxy/Docker process is launched by this static check. Workspace permission metadata is registered by chat catalog reads independently of grants; wildcard write restrictions stay enforced. No runtime checks performed.

## Persistent repository object cache (2026-11-02)
repo_cache.py replaces open_workspace's fresh network clone with a persistent backend-only bare object cache. Default root is <SQLite database parent>/repo_cache; PLATFORM_REPO_CACHE_DIR can override it. Hash namespaces separate organization, connector and case-insensitive GitHub repository. Cache/tenant/entry directories are backend-owned 0700; 0600 no-follow lock files use cross-process POSIX flock (30s acquisition limit). Neither cache nor Git metadata is mounted in the sandbox. No credentials/remotes/helpers are written to cache config; current credentials travel only in the existing sanitized Git environment.
Every use reauthorizes after acquiring its lock, resolves the advertised remote default branch or exact requested branch/tag, then fetches depth=1 into refs/cache/tip with fsckObjects, no tags/submodules/redirects and automatic maintenance disabled. Lookup timeout is30s; fetch retains the existing180s bound. Revocation, cancellation, credential rotation, missing ref or network failure fails closed with no stale/offline fallback. Authorization is rechecked before fetch, before materialization and afterward. Write workspaces still require branch bases; tags are detached read checkouts.
Materialization initializes a new separate gitdir, copies Git objects/shallow boundaries without hard links or alternates, checks out the refreshed commit, and removes the worktree .git pointer. Cache config, refs, credentials, edits and run-created commits are never copied back from executions. Independent object copies allow concurrent runs and cache eviction without corrupting active workspaces. Existing close_workspace still deletes each run's container/worktree/gitdir but retains the shared cache.
Retention is lazy per tenant: PLATFORM_REPO_CACHE_TTL_SECONDS defaults604800 (7 idle days), PLATFORM_REPO_CACHE_MAX_ENTRIES defaults8, PLATFORM_REPO_CACHE_MAX_ENTRY_BYTES defaults536870912 (512MiB). Expired/LRU idle entries are removed under their own locks; busy entries are skipped and may temporarily exceed limits. Oversized entries are not retained after a usable independent checkout is created; these are retention limits, not hard fetch-time disk quotas. Lock files persist to prevent lock-inode races. Cleanup errors defer eviction without invalidating a checkout; refresh/materialization failures invalidate that cache entry. No cleanup daemon or stale branch reuse.
workspace_json.repository_cache and the existing clone_repository audit receipt record {hit,refreshed,retained,commit,base_branch}; hit means an existing cache entry, not measured byte savings. No SQLite schema/API changes or new callable tools. Source contracts in test_repo_cache.py use real local Git/files and no external transport mocks; they were not executed. No tests/build/typecheck/Docker/GitHub/model/workflow calls performed.


notification_guard.deliver_notification adds optional event_key (default complete). Completion keeps legacy call_notify_<execution_id>; start/step events use deterministic hashed suffixes. Audit arguments include event plus destination/message hash. Step events use the corresponding execution step agent; start uses the first explicitly assigned workflow agent captured as context.notification_agent_id when no step row exists. Current tenant/department/initiator/connector/tool/channel policy is rechecked for every send/part. Legacy final bindings retain suppression after an explicit same-destination delivery; new lifecycle modes distinguish task deliveries from progress and do not suppress a requested final report. Atomic claims prohibit automatic repeat of completed/failed/ambiguous sends. No new tables/permissions, retries or externally sent messages in this task.
