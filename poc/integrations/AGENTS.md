# Optional external adapters

`channels.py` contains the single Telegram/Slack message delivery implementation used by MCP verification and workflow notifications. It has no startup/container imports. `find_channel_connector(database, provider, organization_id)` selects a connector only from the supplied tenant's catalog. `resolve_telegram_target` retains configured-chat placeholder resolution. `deliver_channel_message` accepts a configured connector, target and text, sends once with a five-second timeout, and succeeds only after HTTP 200 and provider `ok=true`.

Telegram uses bot_token and chat_id/allowed_channels; Slack uses bot_token and the selected channel through chat.postMessage. Missing credentials/connectors or unsupported providers raise ChannelDeliveryError. Exceptions shown to users omit credential-bearing URLs and provider bodies. There are no automatic retries or simulated successes.

MCP POST `/api/v1/mcp/test-channel-message` returns 503 for an absent connector, 400 for delivery/configuration rejection, and the existing success envelope with delivery=delivered only on acknowledgement. If an audit actor exists, mcp_tool_calls progresses STARTED → COMPLETED or FAILED. No new schema columns are introduced.

WorkflowNotifier is an optional composed adapter; notification exceptions never change workflow execution outcome. Audit IDs use call_notify_{execution_id}; an existing call is not automatically resent. Unconfigured connectors/no audit actors are logged as unavailable without claiming delivery. Delivery acknowledgement/audit are not a transactional exactly-once guarantee; no outbox or retry worker is introduced. All source files stay at most 500 physical lines. No messages were sent and no runtime checks were performed in this task.

## Governed workflow execution tools
New modules are independent of backend startup/router imports:
- tool_definitions: hard-coded executable inventory, strict Pydantic RepositoryInput(repository,days=7,1..90) and MessageInput(channel_id,text<=3500), real resource ID validation, and deterministic implementation metadata registration. Canonical GitHub tools are get_repository_activity/list_commits/list_issues/list_pull_requests/list_releases; Telegram send_message and Slack post_chat_message. Unknown providers/actions are unsupported, never simulated. ensure_tools may register missing mcp_tools metadata but never creates/changes grants. Department wildcard grants cover newly registered implemented tools; explicit lists must include the requested names.
- tool_scopes: execution/step snapshots in server-owned SQLite records. Bound org/department/workflow/execution/task/agent/current initiator; declared connectors/resources/tools cap access. All steps of an integration-backed workflow receive a scope, even model-only steps with no tools. Empty agent permission configuration delegates only the explicitly governed workflow scope; nonempty agent config/database grants further restrict tools. dangerously_skip_permissions never bypasses connector policy. Live task/execution, expiry, initiator status/role/membership, current agent/tenant, connector status, resource allowlists, department/tool grants and budget are rechecked per call. Permission/config growth cannot expand a captured scope; revocation invalidates use.
- provider_http: stdlib HTTPS to fixed api.github.com/api.telegram.org/slack.com hosts, verified TLS, 10-second socket timeout, <=2 MB responses, no redirects, proxy inheritance, caller URLs, credential-bearing logging or automatic retries. Provider bodies/headers are excluded from errors.
- github_activity: authenticated read-only commits/issues/PRs/releases, API version 2026-03-10, UTC lookback and bounded pagination (3 pages of50 per category; <=45000 projected content characters). Issues/PRs use updated_at; releases use published_at; ordinary tags are excluded. Cap-hit output explicitly marks partial=true. Only selected fields are returned, tagged untrusted_external_data; no repository script/content executes. Permissions are rechecked before/after each HTTP request.
- scoped_channels: literal Telegram numeric IDs/@channel usernames or Slack C/G IDs; no alias guessing, first-channel fallback, Markdown execution, external link previews or arbitrary methods. Slack mention/control delimiters are escaped. Sends succeed only on HTTP200 and provider ok=true. A dispatched message cannot be rolled back by later cancellation.
- tool_executor: runtime tool schemas narrow repository/channel enums to the frozen scope; model-supplied credential/URL/identity fields are forbidden. Each actual invocation atomically claims a deterministic call_exec_ audit ID before I/O; at most32 new connector calls per step. Duplicate reads reuse a successful receipt after fresh authorization. Delivery is at most one attempted message per task/connector/channel; changed text or unknown/failed attempts are not retried. Calls progress STARTED→COMPLETED/FAILED. Known denied tools use call_denied_ FAILED audits without hostile arguments. Message audits store only channel ID + text SHA256, not message bodies or credentials. Read results are persisted as private audit data. Completion checks require receipts for every declared repository/channel and explicitly requested operation; prose is insufficient. These are application audit records, not a tamper-proof/exactly-once system.
- notification_guard: frozen completion binding, exact connector lookup, current initiator/grant/tool/channel checks and a real execution agent as audit actor. An explicit successful send step suppresses duplicate completion delivery to that destination. Atomic call_notify_ claims forbid ambiguous resend; notification failure remains an optional delivery failure rather than fabricated success or a changed model result.
Existing channels.py remains the separate legacy manual verification/ChatOps adapter; governed runtime/notification execution uses the stricter scoped_channels implementation. Nothing here is an OS sandbox or a defense against arbitrary trusted backend code. No GitHub writes, GitLab/Trello/SQL/filesystem tools or CLI-MCP bridge are implemented in this version. Tests were added as source only; no execution or live calls were performed.

Optional delivery correction: invalid completion-notification configuration is persisted as notification_error inside workflow_execution_tool_contexts and does not abort authorized data steps. Explicit send steps still fail when their required destination is invalid. A step with authorized_resources uses only the referenced subset of its declared mcp_servers (older builders copied notification connectors into all steps); unrelated connector declarations do not authorize sends. Optional notification failures remain blocked/audited without converting a good summary into a failed model run.

Manual MCP channel tests now reuse scoped_channels, including exact target and provider receipt checks; channels.py remains for legacy ChatOps callers only.

provider_http reads bounded error bodies and maps recognized Telegram rejection descriptions to fixed safe diagnostics (missing chat, bot membership/posting rights, blocked bot, migrated group, bad token, rate limiting). Unrecognized response text, migrated destination values and credentials are never reflected. No permission/target changes or retries occur automatically.

Telegram diagnostics additionally recognize bots-cannot-message-bots, bot-cannot-initiate-user-conversation and deactivated-recipient rejections using fixed safe text. No raw response is exposed and no destination is automatically changed.
